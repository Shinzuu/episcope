\section{Ethical, Societal and Sustainability Considerations}
\textbf{Privacy by design.} No real patient data is used; every encounter is synthetic and labelled so.
Direct identifiers stop at bronze: silver and gold hold only the keyed hash; clean rows keep age bands (the quarantine keeps exact age for review); the key never enters
Git, and every export hides counts from 1 to 4 with complementary suppression, so a total cannot reveal a hidden
cell. One residual risk is known and written in the code: the padded HMAC key appears in Spark's query plan, so
Spark event logs of the silver job must be treated as secret and kept outside the repository. An earlier commit
published unsuppressed backtest cells of the synthetic data; the file is no longer committed.

\textbf{Record-level extracts and public release (PRV-4).} \texttt{pipeline/privacy/kanon.py} measures
k-anonymity~\cite{sweeney2002k} on any record-level extract. It is a check function with unit tests, not a pipeline step: the pipeline publishes only aggregates, so there is no extract for it to check yet. The quasi-identifiers are age band, sex,
district, onset week, disease and facility. k-anonymity does not stop a homogeneity attack, where everyone in a class
shares one diagnosis, so a disease extract also needs l-diversity. For a public release, differential
privacy~\cite{dwork2006dp} is the stronger tool: the Laplace mechanism adds noise with standard deviation
$\sqrt{2}/\varepsilon$ to each count, about 1.4 cases at $\varepsilon=1$. The privacy budget adds up over every
published cell and week, and noisy counts can be negative and must be post-processed. We would use it for the
public release only; ministry users keep exact counts with suppression.

\textbf{Role-based access (PRV-3).} A district user receives a bundle with their own district in detail and
every other area only as a division total. A division total is published only if every district count under
it is visible in the national view. Subtracting one published number from another can then never reveal a
hidden count. An automated security review of the first version found such a leak, and this rule
closes it. The
bundles decide what each role is sent, but a static web server cannot stop a district user from requesting the
national files: a real deployment needs a login and a separate path per role.

\textbf{Equity.} The equity floor gives every district a population share of what is sent, but never more than
it needs. A district that shows no need gets nothing, so the floor cannot protect a district whose reports are
missing. The pipeline keeps such gaps visible instead of hiding them: a district-week in which fewer than 80\%
of the expected facilities reported is marked missing, not zero, and the dashboard shows it as ``no report''.
It does not raise an alert on its own; a reporting-gap alert is left for future work. The floor costs
efficiency, and Section~\ref{sec:alloc} gives the price. The weights in the objective are a value judgement
that the ministry, not the analysts, should own.

\textbf{Misuse and trust.} A named district on an alert list can be stigmatised, and too many false alarms
teach officers to ignore the list; the operating point was chosen to keep false alerts to about two per district
a year for that reason. Big-data signals can drift away from the truth when behaviour or reporting
changes~\cite{lazer2014flu}, so the alerts are a prompt to investigate, not a diagnosis.

\textbf{Footprint.} The whole pipeline runs on one 16\,GB laptop in under 30 minutes at full scale, with no
cluster, cloud service or GPU, which keeps both the energy use and the running cost low enough for a district
office to repeat.
